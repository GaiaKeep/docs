    Two paths through the system¶

    Writing a version. An agent publishes changes to a collection. The block layer splits the new content into blocks and hashes each one. The collection's policy decides whether a block with that hash already exists in the collection's deduplication domain; if so, the new version only references it. New blocks are encrypted and handed to the placement engine. Under the default ec:2+1, each block's ciphertext is split into two data shares and a parity share, one per site, each written to a locus able to show that its writes reach durable storage. The core's replicated log records the version once a majority of the core peers has it. With tape as the primary tier, a durable version then commits when its tape copies are verified; until then reads answer COMMITTING.

    Reading a version. An agent names a version (or an extract) and reads it through the core, which streams it from the nearest copies or stages it from tape first, verifying every block as it streams. In the design of record, prospect returns the options for getting a version somewhere (stream it, recall it from tape first, or send the computation to the data), each with a cost interval and the constraint that binds it, and realise carries one out; the live tier builds the first of these. To a live node, realise makes the version, once committed, into ordinary files that programs read in place; the core registers the copy first and can delete it again (The live tier).

    What runs today¶

    Release 1.3 (2026-10-01) is the storage core that runs on the HPC test deployment, as a Cresco plugin. Core peers keep the core's state in a Raft-replicated log; storage nodes are blind extent stores that hold only ciphertext and answer only the core's signed requests; each site's durable tier is a tape library, on simulated and virtual drives until hardware arrives. Every request is signed, every verb is authorised and audited, and long operations are asynchronous jobs. The deployment runs one Cresco region per site since 2026-10-24/25. See Release 1.3 and Status at a glance.

    Built since, and dated where it is described:

    • Erasure coding ec:2+1 is the default for new collections since 2026-10-14; full replicas and a single copy stay per-dataset choices (Durability).
    • The live tier and the stability work are built and tested on the development branch (2026-10-28), and wait for their gate and a merge: The live tier and Stops, restarts and slow disks.

    The September prototype is retired. Its storage path (a federation index, erasure-coded fragments across sites, a site key in Shamir custody) was removed from the plugin on 2026-10-08; a former index peer reads the prototype's journal once, for the core's legacy import. Its results remain the record of what it proved: see The prototype.

    Not built yet: tape on real drives, raw NVMe and raw disk bindings, and the wider agent interface of the design record (receipts, coverage and purposes, moving computation to the data).
